# K8s Ops Agent v0.2：真实诊断与可靠编排规范

状态：已批准，作为 v0.2 开发与验收基线。

## 1. 目标

v0.2 将现有的确定性示例诊断替换为“真实证据采集 + 可解释规则诊断”，并补齐告警
恢复、异步投递、并发幂等、指标多进程和密钥交付缺口。可选 LLM 只能分析脱敏后的
结构化证据，不能生成或执行命令。

本版本继续保持以下安全边界：

- `AgentRun.mode` 固定为 `DIAGNOSE_ONLY`，诊断路径没有 Kubernetes 写权限。
- 自动修复默认关闭；已有修复仍只允许 Action Catalog 中的低风险动作。
- 所有变更动作必须经过 dry-run、策略检查、审批或显式自动策略、执行审计和结果验证。
- 不把原始告警、日志或 LLM 文本当成可信指令。

非目标：任意 Shell 执行、LLM 自主规划集群变更、跨集群调度、完整 CMDB、无人值守
高风险修复和面向生产的多租户权限系统。

## 2. 交付切片

按以下顺序交付；前一切片测试通过后才能进入下一切片：

1. Evidence 模型、脱敏与限长规则。
2. Kubernetes/Prometheus 证据采集与规则诊断。
3. 可选的结构化 LLM 诊断适配器。
4. Alertmanager `resolved` 生命周期和结果验证。
5. 多进程 Prometheus 指标。
6. Outbox、超时恢复和数据库并发约束。
7. Secret 模板化和部署说明。
8. kind 端到端故障演练门禁。

## 3. 数据模型

### 3.1 Evidence

Evidence 是一次 AgentRun 采集到的只追加诊断事实。

| 字段 | 约束 |
| --- | --- |
| `id` | UUID，主键 |
| `incident_id` | 必填，关联 Incident |
| `agent_run_id` | 必填，关联 AgentRun |
| `evidence_type` | 固定枚举 |
| `source` | `kubernetes`、`prometheus`、`alertmanager` 或 `system` |
| `content` | JSON；只能保存脱敏、限长后的结构化内容 |
| `content_hash` | SHA-256；同一 AgentRun 内用于去重 |
| `redacted` | 是否执行过脱敏 |
| `collected_at` | 服务端时间 |
| `expires_at` | 可选；支持后续数据清理 |

证据类型：`ALERT_PAYLOAD`、`POD_STATUS`、`CURRENT_LOGS`、`PREVIOUS_LOGS`、
`K8S_EVENTS`、`WORKLOAD_STATUS`、`RESOURCE_LIMITS`、`PROMETHEUS_METRICS`、
`REDIS_STATUS`、`COLLECTION_ERROR`。

日志每个容器默认最多 200 行、64 KiB；事件默认最多 50 条；单个 Evidence 的 JSON
序列化结果不得超过 128 KiB。超限内容必须截断并写入 `truncated=true`，不得静默丢弃。

### 3.2 Incident 并发字段

- `occurrence_count` 表示相同活动告警被接收的次数，初始值为 1。
- `version` 仅用于乐观锁，不再承担告警次数含义。
- PostgreSQL 必须对活动 Incident 的 `fingerprint` 建部分唯一索引：状态不是
  `RESOLVED`、`CLOSED` 时只能存在一条记录。

### 3.3 OutboxEvent

API 与领域数据同一事务写入 Outbox，独立 dispatcher 投递 RQ。

| 字段 | 说明 |
| --- | --- |
| `id` | UUID，同时作为队列 `job_id` |
| `topic` | `agent_run.requested` 或 `execution.requested` |
| `aggregate_type/id` | 目标实体 |
| `payload` | 只保存作业标识和安全参数 |
| `status` | `PENDING`、`PUBLISHED`、`FAILED` |
| `attempts` | 投递尝试次数 |
| `available_at` | 下一次可投递时间 |
| `published_at` | 成功投递时间 |
| `last_error` | 限长错误摘要，不写密钥 |

dispatcher 使用 Outbox `id` 作为 RQ `job_id`。即使“队列已接收、数据库尚未标记”时
进程退出，重复投递也不会产生第二个业务作业。

## 4. AgentRun 编排

```text
QUEUED
  -> COLLECTING
       -> EvidenceCollector
  -> DIAGNOSING
       -> RuleDiagnosis
       -> OptionalStructuredLLM
  -> COMPLETED

任一阶段不可恢复错误 -> FAILED + Audit + 人工 Action Task
```

EvidenceCollector 必须通过只读 Adapter 调用，不向诊断器暴露 Kubernetes 客户端。
采集顺序为：告警上下文、目标状态、当前/前次日志、事件、所有者工作负载、资源限制、
相关 Prometheus 指标。单项采集失败写入 `COLLECTION_ERROR`，只要核心目标状态仍可用就
允许降级诊断；所有核心采集失败才令 AgentRun 失败。

RuleDiagnosis 返回固定结构：

```json
{
  "summary": "string",
  "probable_cause": "string",
  "confidence": 0.0,
  "severity": "INFO|WARNING|CRITICAL",
  "evidence_ids": ["uuid"],
  "recommended_actions": [
    {"action_type": "RESTART_POD|INVESTIGATE", "reason": "string"}
  ],
  "diagnosis_code": "CRASH_LOOP|POD_NOT_READY|REDIS_UNAVAILABLE|UNKNOWN"
}
```

首批规则：

- 容器等待原因为 `CrashLoopBackOff`，或前次退出非零且重启数增加：`CRASH_LOOP`。
- Pod Ready 条件为 false，且没有更具体规则：`POD_NOT_READY`。
- Redis 探测或 Prometheus `redis_up` 为 0：`REDIS_UNAVAILABLE`。
- 没有足够证据：`UNKNOWN`，只能创建调查 Task，不能生成可执行 Plan。

规则结果优先。LLM 仅在配置 `DIAGNOSIS_PROVIDER=rules+openai` 时启用；输入是证据摘要，
必须先脱敏和限长；输出必须满足上述 JSON Schema；解析、校验或服务调用失败时回退到
规则结果。LLM 返回的 `recommended_actions` 仍需 Action Catalog 和策略引擎重新校验。

## 5. 告警恢复状态机

Alertmanager `status=firing` 继续执行活动 Incident 去重和诊断触发。

`status=resolved` 时按 fingerprint 查找活动 Incident：

```text
OPEN|DIAGNOSING|DIAGNOSED|PLAN_READY|AWAITING_APPROVAL|FAILED
  -> VERIFYING
      -> 目标健康且关键指标恢复 -> RESOLVED
      -> 验证失败或证据不足 -> FAILED + VERIFY_RESULT Task
```

进入 VERIFYING 后，未开始的 Plan 和 Task 保留但不得自动执行。验证至少读取目标当前
状态；配置了 Prometheus 时同时检查对应恢复查询。只收到 resolved 通知不能直接关闭
Incident。每次恢复通知、验证输入和结论都写 Audit。

## 6. 可靠性与可观测性

### 6.1 多进程指标

Gunicorn 使用多个 worker 时必须设置 `PROMETHEUS_MULTIPROC_DIR`，`/metrics` 使用
独立 CollectorRegistry 和 MultiProcessCollector；worker 退出时清理对应指标文件。
部署启动前清空专用临时目录，不能复用上一次 Pod 的指标文件。

### 6.2 超时恢复

- 超过 `AGENT_RUN_TIMEOUT_SECONDS` 仍在 `COLLECTING/DIAGNOSING` 的 AgentRun 标记失败。
- 超过 `EXECUTION_TIMEOUT_SECONDS` 仍在 `RUNNING` 的 Execution 标记失败，禁止自动重试
  变更动作，并创建人工验证 Task。
- 恢复器必须写 Audit，错误文本脱敏且限长。

### 6.3 Worker 失败语义

作业入口捕获所有未处理异常，在新事务中将业务实体置为失败并写 Audit，然后再抛出
异常交给队列记录。诊断采集允许有限、带退避的读取重试；Execution 不自动重试。

## 7. 密钥与权限

- 仓库只保留 `secret.example.yaml`；真实 `secret.yaml` 被 `.gitignore` 排除。
- 示例不得包含可部署的固定口令或 token，值使用明确占位符。
- Alertmanager webhook token 通过 SecretKeySelector 注入，不写进 Helm values。
- API、worker 和 dispatcher 使用各自 ServiceAccount；诊断路径只有 get/list/watch 权限。
- `OPENAI_API_KEY` 仅在启用可选 LLM provider 时注入，不能出现在 Evidence、Audit、日志
  或 API 响应中。

## 8. API 兼容与输出

现有 API 保持兼容，新增：

- Incident 输出 `occurrence_count`。
- AgentRun 输出 `evidence_ids` 和结构化 `result`。
- `GET /api/agent-runs/{id}/evidence` 返回该次运行的脱敏证据。
- Alertmanager webhook 对 `resolved` 返回 `resolved`、`verification_failed` 或 `ignored`。

接口不返回原始 Kubernetes 客户端对象、完整 Secret、认证头或未脱敏日志。

## 9. 验收门槛

单元/集成测试必须证明：

1. 日志和告警中的 token、密码、Authorization、Cookie 被脱敏，内容被限长。
2. 三类首批规则引用真实 Evidence ID，并对未知情况保持保守。
3. LLM 非法输出和超时会回退，不影响 AgentRun 完成。
4. `resolved` 必须经过验证，失败时创建 Task，不能直接关闭事件。
5. 并发相同 fingerprint 最终只有一个活动 Incident，`occurrence_count` 正确累加。
6. API 提交与队列投递之间进程退出后，Outbox 可恢复且不会重复执行。
7. 多 worker 指标可聚合，退出 worker 不保留脏 Gauge。
8. 仓库不存在真实密钥或可直接使用的默认口令。
9. kind 演练能触发 demo-app 故障、形成 Incident/Evidence/Diagnosis，并在恢复后完成验证。

必须记录无法在当前环境执行的验证项及原因，不得用静态检查冒充真实 Kubernetes 或
Prometheus 验证。
